# @gamehearth/client

The UI of Gamehearth: a PWA that the server serves itself. Built with Preact and Vite.

## Development

```bash
npm run server
```

builds everything (UI, game clients, server) and starts the server on port 8080; the UI is then at http://localhost:8080. For fast work on the UI, run next to it

```bash
npm run dev
```

a Vite server with instant reload that passes `/api`, `/ws` and `/games` on to the server on port 8080 (other server: `GAMEHEARTH_SERVER=http://…`).

## Look: the neon hall

The logo is a joystick whose ball is a flame, games and hearth in one object; the app icon (`public/icon.svg`, `icon-maskable.svg`, PNGs from `npm run icons`) shows it as a neon sign on a dark brick wall, and the mark left of the wordmark is drawn in the style of each theme. The UI is a night-time arcade: a dark brick wall with a horizon and a perspective grid floor, neon tube lettering, the games as arcade cabinets with a glowing marquee, light strips in the game's color and the cover as their screen. It is dark only.

- **Themes.** `<html data-theme="neon">` selects the token block in `src/styles/tokens.css` (colors, fonts, radii, shadows); `base.css` and `screens.css` build every page from these tokens only. Glow, backdrop, cabinet skin and intro live in `neon.css`, all scoped to `[data-theme="neon"]`, on fixed class names (`.backdrop`, `.sign`, `.page-title`, `.cabinet`, `.marquee`, `.screen`, `.deck`, `.room-card`, `.tv-code`, …). The other themes are built the same way (see [Themes](#themes)); the page markup stays the same.
- **Covers.** A game's `cover` is shown with `<img>`; images narrower than 240 pixels are drawn with `image-rendering: pixelated`. Without a cover (or if it fails to load) the UI draws one from the game ID as inline SVG: a color from a hash, a mirrored pixel pattern and the initial. The light strips use the same color. "My rooms" takes the game ID and the cover from the room list (`gameId`, `cover`), so games with the same name keep their own cover and color. Game names on the marquee may take two lines and carry the full name as a tooltip.
- **Font.** Tilt Neon (© 2019 The Tilt Project Authors, SIL Open Font License 1.1) from the npm package `@fontsource/tilt-neon`, pinned like the other dependencies. `fonts.css` points at its `woff2` files (Latin and Latin Extended); Vite copies them into `assets/`, so the service worker caches them with the shell and they work offline; there is no CDN. Only the logo, headings, marquees, codes and buttons use it; body text, forms and lists use the system font.
- **Intro.** On every cold load `main.tsx` sets `data-intro` on `<html>`; the app removes it 1.5 seconds after the first page is ready. While it is set, the tubes flicker on one after another, the cabinet screens switch on and the floor fades in, using only opacity and transform, so they run on the compositor. Nothing waits for it, everything can be tapped at once, and the first page change inside the app ends it at once, so pages opened later play no intro.
- **Motion.** The grid floor drives in once during the intro and then stands; a floor that kept moving cost about 12 % of a CPU core per open page without a graphics card, and nearly nothing else does. `prefers-reduced-motion: reduce` turns off intro, flicker, the arriving floor and the pulsing "Your turn"; the glow stays. The switch "Effects" ("Effekte") in the header and on the account page does the same per device (`gamehearth.effects`, `data-effects="off"` on `<html>`). With effects on, the hall stays alive after the intro with short, stepped flickers on small areas: the "Open" sign and now and then a cabinet's marquee (the CRT monitor flickers its plate and game names the same way). Smooth endless loops on the glowing strips were tried and dropped: they cost up to 94 % of a CPU core with six pages open without a graphics card, the stepped flickers about 1 %; a test allows endless loops only in steps (apart from the small pulsing "Your turn" chip and the buzzing logo letter). After 20 seconds without input (`data-idle`) the endless animations pause until the next touch, key or scroll, which saves battery on a phone lying on the table. The game frame, the single-player page and the TV's game view set `data-scene="play"`, which hides the backdrop; the admin view sets `data-scene="admin"`: same colors and fonts, no animation. Effects are CSS only; there is no blur behind the panels.
- **Sound.** Off by default; the speaker switch in the header, on the account page, in the menu of the game page and of the single-player page and on the TV's pairing page turns it on per device (`gamehearth.sound`). `src/sound.ts` synthesizes short 8-bit sounds with Web Audio, without files: a blip on taps of main buttons, a jingle on joining or creating a room and one at the start of a match, and the games' sounds (see "Sound in games"). Nothing plays before the first tap or key press on the page. On iPhones the ringer/silent switch also applies; the hint on the account page says so. The platform leaves the audio session alone (no `navigator.audioSession`).
- **Same patterns everywhere.** Every page has the same header (back to the home page, title, then a menu or the language switch), its content in bounded panels and its main action in a bar at the bottom (start, create room, play, join, create account, save password). Confirmations use the same dialog, problems the same banners, short messages the same toasts. Touch targets are at least 44 pixels, focus shows a yellow ring, and text meets WCAG AA contrast on its background.

## Themes

Besides the neon hall there are two optional themes on the same pages and building blocks: "CRT monitor" ("Röhrenbildschirm") and "Arcade front" ("Automatenfront"). A theme is one token block in `tokens.css` (`html[data-theme="crt"]`, `html[data-theme="front"]`) plus one decoration file (`crt.css`, `front.css`) scoped to it; markup and layout are the same in every theme. Two shared elements exist only for decorations and are hidden by default: `.glass`, a fixed layer above the page next to the backdrop, and `.bulbs` in the logo with one row of unlit bulbs and three rows of lit ones.

- **CRT monitor.** Dark. The page sits in a monitor housing: `.glass` draws the bezel, the rounded, vignetted tube, a reflection and the scanlines above the content (no scanlines in the admin view, no housing in a running game), on wide screens with the brand plate and a power LED in the lower bezel; the page padding grows by the bezel. Press Start 2P for the logo, page titles, section and card headings and game names; VT323 for buttons, codes, chips, badges, tabs and status lines; body text, forms, lists and the admin view stay in the system font. Square buttons invert on hover, games are little monitors with a power LED, rooms a high-score list. Intro: the power-on line opens into a flash, the logo and the headings are typed, the screens switch on. Loops: the cursor after the logo and the "Your turn" chip blink.
- **Arcade front.** Light, chosen explicitly. A sunburst over cream with doodles, the logo as a light-bulb sign with chaser lights and four pixel sprites, section headings as tilted tags, rooms as tickets with notches, games as cartridges with the name on the label, hard ink shadows. Bungee for headings and buttons, Bungee Shade for the logo, body text in the system font. Text meets WCAG AA on the light surfaces: ink (`#1d1240`) on every tone, the muted text (`#4a3a6a`) at least 4.5:1 also on the sunburst. A running game keeps its dark stage (`color-scheme: dark` on the frame). Intro: the sign drops in and flickers on, the bulbs light one after another, the sprites pop, tags and cards rise, the sunburst turns a little. Loops: the chaser lights (the three rows of lit bulbs take turns, so only three layers change), one bobbing star and the wobbling "Your turn" burst, all in steps.
- **Motion and cost.** The rules of the neon hall apply to every theme: the intro (at most 1.5 seconds, opacity and transform only, never blocking) plays only on a cold load and not after a switch; reduced motion and the switch "Effects" turn off intro and loops; endless animations run only on small elements, in steps where possible, and pause after 20 seconds without input; the admin view and the game frame (`data-scene`) stay calm. A test checks that no theme animates a large area endlessly. With six home pages open and effects on, the test browser without a graphics card uses about 7 / 18 % of a CPU core in the neon hall, 4 / 6 % in the CRT monitor and 7 / 8 % in the arcade front (logged out / logged in with "Your turn"). Smooth endless animations cost far more than stepped ones there: the chaser lights as 40 separately animated bulbs took about 18 %, the bobbing star without steps about 14 %.
- **Fonts.** Press Start 2P (© 2012 The Press Start 2P Project Authors), VT323 (© 2011 The VT323 Project Authors), Bungee and Bungee Shade (© 2023 The Bungee Project Authors), all under the SIL Open Font License 1.1, from the npm packages `@fontsource/press-start-2p`, `@fontsource/vt323`, `@fontsource/bungee` and `@fontsource/bungee-shade`, pinned like Tilt Neon. `fonts.css` uses only their Latin and Latin Extended `woff2` files; Vite copies them into `assets/`, so the service worker caches them with the shell and every theme works offline. A browser downloads a font only when the current theme uses it.
- **Choosing.** Like the language: without a choice the neon hall applies. The switch is a radio group with a preview swatch per theme: a list on the account page, three swatches in the header of the home page while logged out and on the TV's pairing page. The device keeps its choice under `gamehearth.theme`; logged in, a choice also goes to `POST /api/me/theme`, and `theme` from `/api/me` wins on every device of the user. The device keeps a copy of the account's theme apart (`gamehearth.account-theme`, only to start in the right theme); logging out drops the copy and returns to the device's choice. Only a choice made while logged out in this session goes to the account that logs in next, and only if that account has none; an account with its own theme discards it. The TV keeps its choice on the device only. Applying a theme sets `data-theme` on `<html>` and the `theme-color` (`#07030f`, `#0b0b0d`, `#ff8a1f`) and `color-scheme` meta tags; a change applies at once without reload and ends a running intro.

## Languages

The UI speaks German and English. Each language is one file under `src/texts/`; `en.ts` has the type `Texts`, so a missing or extra key is a type error, and a test compares the keys. Another language is one more file plus its code in `languages`.

- **Choosing.** Without a choice the first German or English browser language applies, otherwise English. The switch (on the home page and on the TV) stores the choice on the device under `gamehearth.language`; logged in, it also sends it to `POST /api/me/language`, and the language from `/api/me` wins on every device of the user. The device keeps its own choice apart from a copy of the account's language (`gamehearth.account-language`, only to start in the right language); logging out drops the copy. Only a choice made while logged out in this session goes to the account that logs in next, and only if it has none. The TV keeps its choice on the device only.
- **Texts from manifests** (game names, descriptions, labels of options, items, stats and flags) arrive as `Localized` (a text or one text per language) and are shown with `tr`, falling back to the game's first language. A deleted seat is named by the UI (`memberName`), not by the server's text. Dates and numbers follow the language (`locale()`), and best times use its decimal separator.
- **Games** get their language in every `update` and `solo` message: the UI language if the game lists it in `languages`, then the browser's languages, otherwise the game's first language; games without `languages` get none. A language change reloads the frame. The game list and the game page say "only in German" when a game lacks the UI language.
- **Push** subscriptions carry the device's language; the server puts the user's language into the payload.

## Isolation

The game runs in `<iframe sandbox="allow-scripts">` without `allow-same-origin`; in addition, the server sends a CSP with `sandbox allow-scripts` for every game file (see [packages/server](../server/README.md#http)). So the game can read neither the platform's `localStorage` nor the tokens, and reaches no network via `fetch` or WebSocket. CSP does not govern WebRTC; the games' CSP does list `webrtc 'block'`, but Chromium does not know the directive (and reports it in the console). That is why there are only trusted catalogs, and the dialog when adding one says so (see `docs/design.md`, "Game packages and catalogs"). The page's CSP (`frame-src 'self'`) prevents in Chromium that the game redirects itself to a foreign address; it must therefore not be loosened. The platform accepts only messages whose sender is its own iframe, and checks every move with `parseGameMessage` from the SDK before it goes to the server.

The page itself has a strict CSP: only its own scripts and styles, no inline scripts, `frame-ancestors 'none'`. Inline styles in the markup are therefore off limits; Preact sets `style` objects via CSSOM, which is allowed.

## Login

The session sits in an `HttpOnly` cookie that neither the UI nor a game can read; `localStorage` no longer holds anything secret. On start the UI asks `/api/me`: without a session the home page shows the login and joining by code, guests see their rooms, accounts also the games. Whoever opens a room link joins as a guest with a name or logs in. Links for invite, setup and reset carry their token in the fragment (`#…`), so it is in no request to the server. On the first start after step 5 the UI sends the old room tokens from `localStorage` to the server once and deletes them afterwards.

You get to another device, or into the installed iPhone app, which is logged in separately from Safari, with a transfer code: the account page ("Konto") and the iPhone hint show it with its expiry time and "Copy" ("Kopieren"); the home page accepts it without login or as a guest, in the installed app (`display-mode: standalone`) as the first card. Guests also see "My devices" ("Meine Geräte") on the account page, but can only log out devices there that were added after theirs. Admins get no code and log in with their password. A displayed code shows "expired" ("abgelaufen") after it runs out; after creating, the focus is on "Copy".

## Realtime and TV

Games with the role `screen` need a TV, unless the manifest marks it `"optional": true`. A TV is any device with a browser that opens `/tv`; it needs no account. The page fetches a device cookie and shows a code with a QR code. A member types the code in the lobby under "TV" ("Fernseher") or scans the QR code, which leads to `/pair#CODE` and asks for the room there. A laptop connected to the TV becomes the TV without a code via "Use this device as TV" ("Dieses Gerät als Fernseher nutzen"); on large screens the button is highlighted. The TV then shows the lobby with a large QR code for joining and, during the match, the game in the role `screen`; it keeps the screen on (Wake Lock). A match starts only with a connected TV; the lobby says so. With an optional TV (`screenOptional` in the room's game) the card "TV" says "optional" ("optional") instead of "needed to start" ("nötig zum Starten"), the host can start without one, and a missing TV never pauses the match; pairing and "Use this device as TV" work the same.

Phones in games with the role `controller` are controllers: the bridge gives them the role `controller`; games with the role `player`, with or without a TV, give them `player` as before. Realtime snapshots come as a light `frame` message 20 times per second and replace only the snapshot. The platform announces delta frames (`deltas: true` in `hello` and `screen`), so the server sends only what changed since the last snapshot, for a growing drawing only the new part (see [packages/server](../server/README.md#realtime)). `connection.ts` applies a delta with `applyJsonDelta` from the SDK only onto the snapshot whose `version` is the frame's `base` and passes the whole snapshot into the game frame as before; games notice nothing. If the version differs or the delta does not fit, the platform keeps its snapshot and sends `resync` once; the server then sends the whole snapshot with the next frame, and a `room` or `screen-room` message also ends the wait. There is no "Your turn" in realtime. Above the game the platform shows the countdown (without blocking input), a pause with its reason ("Waiting for Ben" ("Warte auf Ben"), "Waiting for the TV" ("Warte auf den Fernseher"), "The host paused" ("Der Gastgeber hat angehalten")) and an error with incident number. The host pauses from the menu and resumes from the overlay.

The game list names the devices for each game ("TV + phones" ("Fernseher + Handys"), "TV + own devices" ("Fernseher + eigene Geräte"), "everyone on their own device, TV optional" ("jeder am eigenen Gerät, Fernseher optional"), "everyone on their own device" ("jeder am eigenen Gerät")). If the device fits no role of the manifest by width and pointer type, a notice appears; creating a room works anyway, because the browser does not reliably reveal keyboard and gamepad.

## Bots and playing on

Only games whose manifest has a `bot` function offer bots (`bots: true` in the room's game, see [packages/sdk](../sdk/README.md#bots)).

- **Lobby.** The host sees "Add bot" ("Bot hinzufügen") below the members; it is disabled while the room is full. A bot is a member with `bot: n` and an empty name: it is shown as the n-th of fixed playful names in the device's language with a robot sign ("Robo-Rita 🤖", "Blechbert 🤖", "Tin Tim 🤖" …; beyond the list with a counter, "Robo-Rita 2 🤖"), with a badge "Bot" and without the line "not connected". Bots count toward the player count the lobby shows and toward the room's size. The host removes one with "Remove" ("Entfernen"), which sends `kick` without asking, unlike for people. Bots stay members across rounds.
- **Handing a seat over.** In a running match of such a game, the game page's menu offers "Let a bot play for me" ("Bot spielt für mich") for your own seat, and the host gets one entry per seated member without a connected device ("Hand to a bot: Anna" ("An Bot geben: Anna"), also for a deleted seat). Both ask first and send `hand-over` with the member's ID. In the pause of a realtime match the host finds the same button below "Waiting for Anna" for a missing seat whose member has no connected device. Refusals of the server (`not-host`, `not-running`, `no-bots`, `unknown-member`, `member-connected`, `already-bot`, `not-in-lobby`, `room-full`, `not-handed-over`) appear as a toast in both languages.
- **Autopilot.** While a bot plays your seat (`you.autopilot`), the game page lays "A bot is playing for you" ("Ein Bot spielt für dich") with "Back into the game" ("Zurück ins Spiel") over the game, which stays visible behind it; the button sends `take-back`. Elsewhere a seat on autopilot keeps its name with a robot sign ("Anna 🤖"). The game gets bot seats and seats on autopilot as `bot: true`, `connected: true` and with these names. A new round ends the autopilot.
- **Away seats.** In a realtime match of a game with `"away": "play-on"` the server lists seats that are away in `live.awaySeats` instead of pausing. The game page names them quietly after the room code in the bar ("away: Ben" ("weg: Ben")), the TV in its bottom strip; nothing is paused or covered.

## Sound in games

A game plays sounds through the platform (`game.sound(…)`, see [packages/sdk](../sdk/README.md#sound)). The bridges of the game page, the single-player page and the TV pass the device's switch to the game (`settings` after `ready` and on every change) and forward the game's sounds only while it is on. `src/sound.ts` turns a sound into notes with `soundNotes` from the SDK and plays them with the envelope of the platform's own cues; a note's volume from 0 to 1 becomes a peak gain of `volume × 0.12`. Each game frame plays at most 12 sounds per second and drops the rest. Taps inside the sandboxed game frame do not reach the platform's listeners, but they give the top window user activation, so sound plays once the page has seen a tap or key or `navigator.userActivation.hasBeenActive` is true. The TV's switch on its pairing page is its own device setting; its click creates and resumes the audio context, so the TV plays the shared sounds later without another click. A TV that reloads in the middle of a match needs a click on its page before it plays again.

## On-screen keyboard

The viewport meta in `index.html` has `interactive-widget=resizes-content`: on Android the page shrinks when the on-screen keyboard opens. The game frame (`.play`, fixed to the viewport) then covers only the area above the keyboard, and the game gets a `resize` and lays out its content and input field in the rest. On the other pages the main action bar sits directly above the keyboard, and dialogs and toasts stay in view. iOS ignores the setting: Safari keeps the page size and scrolls the focused field into view instead, so a game keeps its input field directly below what it belongs to. Browser tests cannot open an on-screen keyboard; Safari on a real iPhone and Chrome on a real Android phone are checked by hand.

## Single player and offline

Single-player games without a reducer (`mode: "single"`, `server: false`) are played without a room: "Play" opens `/play/<id>`, and the game talks to the platform through `connectSolo` (see [packages/sdk](../sdk/README.md#single-player-without-a-reducer-connectsolo)). Only accounts see and play them.

- **Saving.** Save and best scores land in the platform's `localStorage` right away, separately per account; the game itself has no storage. The sync with the server (`POST /api/solo/<id>/sync`) runs bundled 2 seconds after a change, when leaving the page, when the app goes to the background, after loading and when the network comes back. For the save, the newer one by the device clock wins; for best scores, the better one. Deleted saves stay on the server as a mark with a timestamp, best scores have a deletion counter; so a device that was offline for a long time brings nothing deleted back. Several tabs or windows share the storage: each re-reads it before every read and change, so none overwrites the state of another.
- **Preload.** Online, the home page preloads the current build of every installed single-player game once: a hidden `<iframe sandbox="allow-scripts">` opens `/preload/1` and fetches all files (`GET /api/solo/<id>/files`, plus the folder address under which the game is opened) with `cache: "force-cache"` into the browser's HTTP cache. The service worker does not see requests from sandbox iframes; the HTTP cache serves them because the server delivers game files as `immutable`. Preloaded from the platform's window, WebKit would not find the files later (the cache there is partitioned by the frame's origin), hence the detour through a sandbox frame.
- **Start.** Online, the single-player page first fetches the game list and the save from the server, each for at most 4 seconds. If the game list does not answer, it takes the offline path including the check. If a sync after the start brings a different save than the game got (e.g. from another device, on a slow network), the page reloads the game with it and says so; otherwise the next `save` would overwrite the newer state.
- **Offline.** Without connection the home page shows "Offline playable" with the games of the last logged-in account. Before the start the single-player page checks through the same frame whether all files are still in the cache (at most 15 seconds), and says so if the browser has cleared them. If a game does not respond after 12 seconds, a notice appears.
- **Logout** syncs first (at most 3 seconds) and then deletes the single-player data of this account on the device; what could not be synced stays on the device until the same account logs in again. In no case does the account stay offline playable afterwards: "Offline playable" shows only the last logged-in account, and logging out forgets it. If the session has expired meanwhile, pending changes likewise wait for the next login.
- **Limits.** In private mode (Safari, Firefox, Chrome incognito) there is no persistent cache; there offline works only while the window is open, in WebKit not at all. Firefox is not tested for offline play. Full device storage makes `game.save()` and `game.record()` fail with a message.

## Game page and profiles

Every game has a page at `/game/<id>` (`GET /api/games/<id>`, see [packages/server](../server/README.md#profiles)), reachable via the name in the game list.

- **Profile.** Your own profile is shown by section ("Items" ("Gegenstände"), "Values" ("Werte"), "Unlocked" ("Freigeschaltet")) with the display names and in the order of the manifest; values with `format: "time"` as time, flags with `true` as "yes" ("ja"), deprecated entries with "(deprecated)" ("(veraltet)"). IDs that the installed build no longer knows are not shown on the game page; the admin view shows them. Guests see, instead of a profile, a sentence on why they have none.
- **Leaderboards.** Per stat with `better`, the top 10 accounts of the server; your own entry is highlighted, and appended with its rank if it is further down. For single-player games it says "reported by the device" ("vom Gerät gemeldet").
- **Reset.** "Reset profile" asks first and works only with a connection. For single-player games the page then syncs with the server so the device clears its old best scores.
- **Offline.** The page remembers its last state per account in `localStorage` and shows it without connection with the note "State of the last connection" ("Stand der letzten Verbindung"); "Offline playable" on the home page links the saved pages of games with a reducer. Logging out deletes them, on the home page as on the invite page.
- **In the game.** Your own profile comes with every snapshot of the room (`room.profile`) and goes to the iframe as `update.profile`, even when another match changes it. If the server rejects a move with `missing-item`, the platform shows a short notice.

## PWA

- `public/manifest.webmanifest` with icons and the dark background `#07030f` as background and theme color (the page's `theme-color` meta follows the chosen theme); the PNG icons are made from the SVGs with `npm run icons` (Playwright) and are in the repo.
- The service worker caches only the shell (index.html, hashed files, manifest, icon). Page requests go to the network first; without network the app starts from the cache and reports "No connection to the server" ("Keine Verbindung zum Server"). It never touches `/api`, `/ws` and `/games`; single-player games come from the HTTP cache offline (see above).
- A new version of the server brings a new service worker that takes over at once and deletes old caches.
- Without connection, the "No connection to the server" notice also mentions the home network and VPN, because otherwise a tap on a notification on the go leads nowhere when the server is only reachable at home.

## Notifications

- They are turned on per device on the account page or via the hint that "My rooms" shows during a running match and that the lobby shows. The browser asks only after the tap. The device remembers "Not now" ("Nicht jetzt") in `localStorage`. On iPhone and iPad in a Safari tab there is no `PushManager`; there the hint explains how to add the app to the home screen, and adds that the installed app is logged in separately (accounts log in again, guests cannot get to their seats there).
- The subscription is created with the server's public key (`GET /api/me/push`). If the browser already has a subscription with a different key, e.g. after a new server, the UI cancels it and creates a new one. Turning off also cancels the subscription in the browser. If push is on for this session, the UI registers the browser's subscription again once on first load, in case the browser renewed it without the server learning about it.
- The room connection sends in `hello` and on every `visibilitychange` whether the app is visible; only then does the server hold back pushes for this room. Opening a room or bringing the app to the front clears its notifications.
- The service worker shows every push, even a broken one (otherwise browsers revoke the subscription), with the room code as `tag`, so only the newest notification per room remains. On "Your turn" it sets the app badge. A tap brings an open window of the app (not a tab with an API response) to the front and sends it into the room by message, or opens a new one; only paths of the app are accepted (`/`, `/r/<code>`, `/account`). If the browser renews a subscription (`pushsubscriptionchange`), the service worker reports it together with the old endpoint to `POST /api/me/push/renew`; another user who has logged in on the device meanwhile thus gets no subscription. The texts come from `pushTexts` in `src/texts.ts` at build time, one set per language; the service worker takes the set named by `lang` in the payload and English without one.
- Lobby and game menu mute or unmute a room; "My rooms" shows "muted" ("stumm").

## Tests

`npm test` tests the logic (connection, bridges, storage, sync, preload, push) and the screens (with happy-dom), and the service worker with mocked browser APIs. Whether sandbox, CSP and `postMessage` hold in a real browser and whether a push arrives from the move to the tap is checked by `npm run e2e` (see the root README); `e2e/solo.e2e.ts` plays the test game Sammler (collector) with save, best score, leaderboard and offline start in Chromium, `e2e/solo-webkit.e2e.ts` starts it offline in WebKit with its own profile, without having played it online before.
